# 架构说明

## 分层

```
run.py                     入口：create_app() → app.run()
└── app/__init__.py        create_app 工厂：日志、建表、注册蓝图、启动调度器
    ├── routes/            表现层：只做参数校验与 JSON 序列化
    │   ├── pages.py       /  /api/health  /api/logs
    │   ├── groups.py      /api/groups/**
    │   ├── mailboxes.py   /api/mailboxes/**（含 /import）
    │   └── emails.py      /api/emails/**
    ├── services/          业务层：编排外部调用与本地存储
    │   ├── client.py      OneTimeEmailClient + SiteError + normalize_emails
    │   ├── mailbox_service.py  创建/同步/续期/删除
    │   ├── group_service.py    分组：多级树、防环、级联删除
    │   ├── importer.py         导入：解析文本/Excel、校验 uuid、去重入库
    │   └── renewer.py     RenewScheduler 后台线程
    ├── store.py           数据层：所有 SQL 集中于此
    └── database.py        连接、WAL、建表
```

依赖方向单向：routes → services → store → database。store 不认识 services，services 不认识 Flask。

## 一次创建请求的完整链路

1. 前端点「新建临时邮箱」→ `POST /api/mailboxes {auto_renew:true}`
2. `routes/mailboxes.py:create_mailbox` 调 `mailbox_service.create_mailbox`
3. `OneTimeEmailClient` 新建 `requests.Session`（独立 cookie 罐）
4. `GET /zh-hans/` 拿页面 → 正则抽 `csrf-token`，同时拿到 `PHPSESSID`
5. `POST /zh-hans/create_inbox.php`，带头 `X-CSRF-Token`、`X-Requested-With`、`Origin`、`Referer`
   - 若 403：重新取一次 token 再试一次（对齐官方前端行为）
6. 返回 `{email, uuid, recovery_phrase, lifetime:"1h"}`
7. 立刻 `POST /api/api_update_lifetime.php`（uuid + 30d）把有效期改成 30 天
8. Cookie 序列化成 `PHPSESSID=xxx; preferred_language=zh-hans` 存入 `mailboxes.cookies`
9. 写库，返回邮箱对象

## 一次收信

`POST /api/mailboxes/:id/refresh`
→ 读库取 uuid/cookies → `GET /api/api_check_emails.php?uuid=...`
→ `normalize_emails()` 统一字段名 → `store.upsert_email()` 逐封入库（已存在则更新正文）
→ 回写 `last_checked_at`、`lifetime`、`cookies`，有新邮件才写日志。

前端选中邮箱时会自动 refresh 一次，之后每 30 秒静默轮询当前邮箱。

## 自动续期

`RenewScheduler`（daemon 线程）启动后等 5 秒，然后每 `SCHEDULER_TICK_SECONDS`（默认 300 秒）跑一轮：

```
store.list_due_for_renewal()
  WHERE auto_renew = 1 AND status = 'active'
    AND (last_renewed_at IS NULL OR last_renewed_at <= now - 24h)
```

命中就调 `mailbox_service.renew_mailbox()`。单封失败只记日志，不影响其它邮箱；成功写 `last_renewed_at`。

> 为什么不会重复续期：每成功一次就把 `last_renewed_at` 推到当前时间，下次要再等 24 小时才命中。

## 一次导入的链路

1. 前端三种入口最终都变成「一段文本」或「一个 xlsx 文件」：
   - 粘贴文本 / 文本文件 → 文本框内容 → `POST /api/mailboxes/import`（JSON）
   - Excel → `POST /api/mailboxes/import`（multipart）
2. `routes/mailboxes.py:import_mailboxes` 按扩展名分流：xlsx 走 `importer.import_from_excel`，其余走 `import_accounts`。
3. `parse_text()` 逐行用正则找 uuid（`8-4-4-4-12`），剩下的文本当助记词；表头行按关键字跳过，没有 uuid 且不像表头的记入 `invalid`。
   Excel 的做法是**把每行单元格拼成一个字符串**再交给同一个解析器，所以列顺序、有没有表头都不影响。
   xlsx 由 `services/xlsx_reader.py` 解析：直接读 zip 里的 `workbook.xml` / `sharedStrings.xml` / 第一个 sheet 的 XML，
   只用标准库，避免 openpyxl 把编译时间从 3 分钟拖到 10 分钟。
   模板下载走 `services/xlsx_writer.py`，同样是标准库拼 5 个 XML 文件（inlineStr 写法，无需 styles/sharedStrings），
   生成的文件 Excel / WPS / 本项目读取器都能正常打开。
4. `_run()` 逐行处理：
   - uuid 已在库 → `duplicated`
   - 本批次内重复 → `duplicated`（提示与第几行重复）
   - 调 `check_emails(uuid)` 换回邮箱地址并验证有效性；失败 → `failed`
   - 地址已在库 → `duplicated`
   - 入库（`mailbox_type=1`、写入目标分组），顺手把返回的邮件也缓存下来
5. 返回 `{imported, duplicated, invalid, failed, total}`，前端渲染成四个色块清单 + 每项明细。

> 导入**不需要 Cookie**，因为没有走创建流程；uuid 本身就是凭证。

## 抓信与续期（2026-11-06 重构）

**抓信不再自动轮询。** 历史版本前端每 30 秒打一次 `/refresh`，失败也不退避，导致日志里
成片的 502。现在改成「用户手动触发 + 后台按间隔执行」：

```
前端「抓取邮件」→ 选择树（全部 / 整组 / 单个）→ 确认清单
   → POST /api/jobs {kind:"fetch", scope:"ids", ids:[...]}
   → jobs.JobManager 起后台线程
   → 逐个邮箱：sleep(间隔) → svc.refresh_mailbox(id) → 记录结果
   → 前端每 700ms 轮询 GET /api/jobs/:id 渲染进度与明细
```

- 间隔来自数据库里的配置（`settings_kv.config` 的 `fetch` 段），支持固定毫秒或 [min,max] 随机
- 同一时刻只允许一个任务（`JobBusy` → 409），避免两批请求交叉让间隔失效
- 任务进度与每条结果**实时写库**（`jobs` / `job_items`），所以关网页、刷新页面都不丢
- 进程重启时，上次遗留的 `running` 任务会被标记为 `interrupted`（线程已不存在），历史里能看到中断前完成了多少
- 取消是「软取消」：当前这封跑完就停，不会硬杀线程

### 任务持久化与恢复

```
jobs            id/kind/status/total/done/current/lifetime/started_at/finished_at/error
job_items       job_id/seq/mailbox_id/email/ok/new_count/error/at
```

- `create_job()` 时把目标一次性写进 `job_items`（seq 即执行顺序），每处理完一个就更新那一行
- 前端打开页面 → `GET /api/jobs/active` → 有 running 任务就自动打开面板、接上轮询
- 面板关掉后按钮上仍显示 `抓取邮件 2/5`，靠 2.5 秒一次的后台轮询更新
- 历史列表读 `GET /api/jobs`（默认最近 30 条），保留上限 200 条（`prune_jobs`）

**续期拆成两层**：调度器只决定「什么时候开跑」，任务引擎负责「怎么跑」。

```
renewer.RenewScheduler（每 30 秒巡检）
  ├─ mode=interval：now - last_run >= interval_hours → 触发
  ├─ mode=daily  ：now >= daily_time 且今天没跑过 → 触发
  └─ 触发 = jobs.create("renew", 所有 auto_renew=1 的邮箱, lifetime=配置值)
```

触发时间存在 `settings_kv.scheduler`（`last_renew_run` / `last_daily_date`），
所以重启不会重复触发，也不会漏掉当天该跑的一次（启动晚于 daily_time 会补跑）。

## 分组

- 表 `groups` 用 `parent_id` 自引用，层级不限。
- `group_service.update_group` 用 `descendant_group_ids` 做防环校验：不能把分组挪到自己或自己的子孙下面。
- 删除分组是**级联**的：递归删掉所有子分组，组内邮箱 `group_id` 置空（回「未分组」），邮箱本身不删。
- 前端筛选用的是「子树包含」：选中父分组会显示其所有子孙分组里的邮箱（`app.js: subtreeIds`）。
- 分组计数也是子树口径，`store.list_groups` 只返回直属数量，前端用 `countOf()` 汇总。

## 数据库表

### mailboxes

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| email | 邮箱地址，唯一 |
| uuid | 站点凭证，唯一。**等同密码** |
| recovery_phrase | 12 词恢复短语 |
| lifetime | 当前有效期，如 `30d` |
| auto_renew | 1 开启每日自动续期 |
| cookies | 创建时的 Cookie 字符串 |
| note | 备注，最长 200 字，服务端 trim 后截断 |
| mailbox_type | 邮箱类型，当前固定 1。API 对外字段名是 `type` |
| group_id | 所属分组，可空（未分组）；删除分组时置空 |
| status | `active` / 保留字段 |
| created_at | 本地时间字符串 |
| last_checked_at | 上次收信时间 |
| last_renewed_at | 上次续期时间（调度器据此判断） |
| last_error | 最近一次失败原因，成功后清空 |

### settings_kv

| 字段 | 说明 |
| --- | --- |
| key | `config`（抓信/续期配置 JSON）或 `scheduler`（上次触发时间） |
| value | JSON 字符串 |

### jobs

| 字段 | 说明 |
| --- | --- |
| id | 12 位十六进制串 |
| kind | `fetch` / `renew` |
| status | `running` / `done` / `cancelled` / `interrupted` |
| total / done / current | 进度 |
| lifetime | 续期任务使用的有效期 |
| started_at / finished_at | 本地时间 |

### job_items

一行一个目标邮箱，`seq` 与执行顺序一致；`ok=0 且 error` 为空表示"还没轮到"。

### groups

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| name | 分组名，同层不强制唯一 |
| parent_id | 上级分组，NULL 为顶层 |
| created_at | 创建时间 |

### emails

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| mailbox_id | 外键，手动级联删除 |
| remote_id | 站点邮件 id，与 mailbox_id 组成唯一键，防重复 |
| sender / subject / received_at | 展示用 |

### 日志体系（四通道）

| 通道 | 表 | 记录内容 | 保留 |
| --- | --- | --- | --- |
| 业务 | `logs`（action 非 system/server） | 创建/抓信/续期/删除/导入/清空 | 2000 条 |
| 系统 | `logs`（action=system/server） | 启动、中断任务标记、500 异常摘要 | 同上 |
| 前端请求 | `access_logs` | method/path/query/状态/耗时/ip/请求体（文件类只记文件名） | 5000 条 |
| 外部请求 | `http_logs` | 对站点的每次请求：URL/状态/耗时/请求体/**响应体**/错误，可关联 job_id 与 mailbox_id | 2000 条 |

**脱敏策略：入库原文、出口脱敏。**

- 写入：`trace.record_http()` 默认不脱敏（排查问题需要完整凭证），`trace.sanitize()` 只在出库时调用
- 读取：`GET /api/logs` 对 `access_logs` / `http_logs` 统一脱敏（uuid 只留前 8 位、recovery_phrase 与 PHPSESSID 打码）；诊断时可用 `&raw=1` 取原文
- 自查：`_LOG_WRITE_COUNTER` 每 50 次写入顺手裁剪；`add_*_log` 自身失败吞异常，不影响主流程
- 前端请求日志跳过 `/static/`、`/favicon.ico` 与 `/api/logs` 自身（防刷屏与递归）

`tempmail.log` 已停止写入（运行日志全部入库，进程日志只走控制台）。

### logs

`level / action / mailbox_id / message / created_at`。

- 写入点：`store.add_log()`，覆盖创建/抓信/续期/删除/导入/清空/500 异常
- 读取：设置面板底部「运行日志」（`static/logs.js`），支持按级别过滤、清空
- 维护：超过 2000 条自动裁剪最旧的；`add_log` 本身失败不会影响主流程（吞异常）

## 前端结构

前端拆成 4 个文件，加载顺序 api → groups → importer → app（app 最后启动）：

- `static/api.js`：`API.*` 一组方法，统一处理 JSON、`success:false`、非 JSON 响应、FormData 上传。
- `static/app.js`：核心 IIFE，含 `state`、分组辅助（`subtreeIds`/`childGroups`）、邮箱列表、邮件、备注、启动与轮询；末尾把 `state`/`el`/工具函数挂到 `window.TM`。
- `static/dialog.js`：通用弹窗（输入框/确认框），替代原生 `prompt`/`confirm`，暴露 `window.TMDialog`；
  带进出场动画、Esc/遮罩关闭，危险操作红色确认按钮。
- `static/groups.js`：分组树渲染与增删改 + 同级拖动排序（HTML5 Drag & Drop，drop 后调
  `POST /api/groups/reorder` 重写 `sort_order`），通过 `window.TM` 读写共享状态，暴露 `window.TMGroups`。
- `static/importer.js`：导入弹窗，三个页签 + 结果面板，暴露 `window.TMImport`。
- `static/jobs.js`：批量抓信/续期面板，三步（选择树 → 确认 → 进度），进度靠轮询 `/api/jobs/:id`。
- `static/settings.js`：设置弹窗，读写 `/api/settings`，字段按模式动态显隐。

> 两个附属模块只在**事件触发时**才访问 `TM`，所以加载顺序上只要保证 `app.js` 最后执行即可，不存在初始化环。
- 渲染全部走模板字符串 + `esc()` 转义，避免邮件标题里的 HTML 注入页面。
- 邮件正文在 `<iframe sandbox="allow-popups ..." srcdoc="...">` 里渲染，并附 CSP `default-src 'none'`，脚本、表单、内联事件全部失效，只允许图片。
- 弹窗 `#modal` 用于「放大查看」：每次打开都会重建 `#modal-frame`（新节点 + 先显示后写 srcdoc），
  避免复用 iframe 时重复赋值 srcdoc 不重新导航导致第二次打开白板；关闭时移除 srcdoc 释放文档。
- 弹窗 `#note-modal` 用于编辑邮箱备注：卡片上的「加备注 / 改备注」按钮打开，`state.noteId` 记住目标邮箱，保存走 `PATCH /api/mailboxes/:id`，支持 Ctrl+Enter 提交、Esc 关闭、实时字数统计（上限 200）。

## 数据库结构版本化迁移

`app/migrations.py`：`schema_version` 单行表记录当前版本；`MIGRATIONS = {版本号: 升级函数}`，
`STRUCT_CHECKS = {版本号: 结构是否已满足}`。启动时 `database.init_db()` 做完整校验并升级；
每个新连接只读一次版本号（`migrate(conn, verify=False)`），不做结构比对，避免每请求都跑 PRAGMA。

`migrate()` 的判定顺序：

1. 没有版本记录时——没有 `groups` 表视为全新库（建表语句已是最新），直接标最新；
   有业务表视为无版本表时代的老库，从 v0 开始升。
2. 真正需要执行升级函数时，先用 `conn.backup()` 把整库快照成 `tempmail.db.bak-v<旧版本>`
   （同名已存在则追加时间戳），备份失败不阻断升级。
3. 逐版本执行迁移函数并写 `schema_version`；结构已满足该版本的（如全新库）只补版本号、不备份。
4. 升级结果写一条 `logs`（`action=db_migrate`）并在控制台打印；同时把升级信息写进
   `settings_kv` 的 `db_upgrade_notice`，首页由 `pages.index` 渲染顶部提示条（`#db-notice`），
   「知道了」按钮调 `DELETE /api/db-notice` 清掉该 key，只提示一次。
5. `schema_version > LATEST_VERSION`（用老程序打开新库）直接返回，不降级、不改库。
6. 兜底：版本号声称最新但列被外部改没（`verify=True` 时比对），视为 v0 重跑，迁移幂等。

原则：只加列/加表/回填，绝不删改原数据。
- **v1**：`groups.sort_order`、`mailboxes.sort_order`（拖动排序），老数据按 id 回填 1..N。
- 手动执行：`python -m app.migrations [db路径]`，会打印本次升级版本与备份文件名。
- 新增迁移时：写 `_migrate_to_vN` → 注册 `MIGRATIONS` → 写 `_struct_ok_vN` 注册 `STRUCT_CHECKS`
  → `LATEST_VERSION` 改为 N → 同步 `database.py` 的 `SCHEMA`（全新库建表即最新）。

`store.py` 列表查询均按 `sort_order` 排序；新建分组/邮箱自动取 `MAX(sort_order)+1`。
重排接口：`POST /api/groups/reorder`、`POST /api/mailboxes/reorder`（body: `{"ids":[...]}`）。

## 打包要点

`build.py` 用 Nuitka 编译，关键是两个 `--include-data-dir`，把 `app/templates` 和 `app/static` 塞进产物；`config.py` 的 `_base_dir()` 判断 `sys.frozen` / `__compiled__`，让 `data/` 落在 exe 同级目录而非临时解包目录。

单文件模式下 Nuitka 会把资源解到临时目录，此时 `RESOURCE_DIR` 指向解包目录，Flask 的 `template_folder="templates"` 正好命中 `app/templates`。

## 有效期选择与未读角标

- 顶栏「有效期」下拉由服务端渲染（`pages.index` 传 `lifetime_choices()`），选项来自
  `config.LIFETIME_OPTIONS` + `LIFETIME_LABELS`；`localStorage["tm.createLifetime"]` 记住上次选择。
  新建时 `POST /api/mailboxes` 带 `lifetime`，`mailbox_service.create_mailbox` 调站点
  `api_update_lifetime.php` 把默认 1h 改成所选值；服务端再次校验白名单，非法值直接 400。
- 未读角标：`store.list_mailboxes()` 聚合 `is_read = 0` 得到 `unread_count`。
  `GET /api/emails/<id>` 返回前会置已读，所以前端**不能在响应体里判断**是否刚从未读变已读；
  `openEmail()` 改为请求前记录 `wasUnread`，读后 `loadEmails()` + `syncUnreadBadge()`
  把卡片未读数减一并重绘，无需刷新页面。

## 分组树拖动与批量移入

- **展开标记**：`.g-caret` 由 12px 纯文字改成 18px 圆角按钮（浅底+描边），展开时旋转 90°；
  只有含子分组的分组才渲染，无子分组用 `.g-caret.ghost` 占位保持缩进对齐。
- **分组拖动**（`groups.js`）：`zoneOf()` 把行高分成上 30% / 中 40% / 下 30%。
  中区 = 放入目标分组（`PATCH /api/groups/:id {parent_id}`，自动展开目标）；
  上下区 = 仅同父级时做同级排序（`POST /api/groups/reorder`）；跨层级时一律按放入处理。
  拖到「未分组」行 = `parent_id: null` 回顶层。用 `TM.subtreeIds(src).has(dst)` 阻止拖进自己或子孙。
- **邮箱拖入分组**：卡片 `dragstart` 写入自定义 MIME `application/x-tm-mailbox` 与
  `window.TM.draggingMailboxIds`（拖已勾选卡片时带上整批）；分组树各行 `dragover` 用
  `dataTransfer.types` 判断是邮箱拖动，`drop` 调 `POST /api/mailboxes/move`。
- **批量管理**：`state.selectMode` + `state.selected`；开启后卡片显示复选框、隐藏操作按钮、
  禁用拖动，点卡片即勾选；`TMDialog.select()`（新增的下拉弹窗）选目标分组后调同一个 move 接口。
